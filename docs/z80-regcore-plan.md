# Ядро Z80 с регистрами в регистрах ARM: анализ и план (2026-11-15)

Статус: **этапы 0 и A сделаны 2026-11-15, не закоммичены**; на железе (DVp2w,
`debug/DVp2w-regcoreA-1.1.2.elf`, 2026-11-15) владелец: «неплохо, некоторые игры точно
ускорились, глядя на IDL» — по играм не расписано, цифр FPS/IDL нет. Этапы B и C не начаты. Итог этапа A и то,
что он изменил в оценках, — в разделе 8; подробности в `docs/notes/z80-core.md`.
Разделы 1-5 — исходный разбор: цифры «сейчас» там сняты статически с
`debug/DVp2w-nav256-1.1.2.elf`, цифры «после» — оценка до начала работ.

## 1. Что есть сейчас

Три цикла исполнения в `src/speccy/z80/Z80_JLS.cpp`:

| Цикл | Для кого | Диспетчер | Где живёт |
|---|---|---|---|
| `exec_nocheck` | все машины, общий путь | `dcOpcode[op]()` | SRAM, 2220 B + обработчики |
| `exec_nocheck_ts` | TS-Conf / ATM / 16col (`g_ts_fastmem == 2`) | `dcOpcode[op]()` | SRAM, 272 B |
| `exec_nocheck_next` | Next (`g_next_fastrd`) | `switch`, тела вставлены генератором `tools/gen_next_dispatch.py` | `.nxovl`, 13 644 B |

Всё состояние Z80 — статические поля класса (`regA`, `sz5h3pnFlags`, `carryFlag`, `regBC`…,
`regPC`, `flagQ`, `lastFlagQ`, `pendingEI`, `prefixOpcode`, `memptr`). В регистрах ARM в цикле
Next живут только T-счётчик (`nx_t`, r5) и R (`nx_r`, r7); остальные регистры заняты адресами
(база состояния r4, `&ts_line_t` r8, `&stFrame` r9, `&tstates` r10, таблица страниц r11).

### Цена одной инструкции Z80 в цикле Next (ARM-инструкции, по дизассемблеру)

Постоянная часть, платится на КАЖДОЙ инструкции:

| Что | ARM insn |
|---|---|
| загрузка `ts_line_t`, +4 T, сравнение, переход | 4 |
| загрузка PC из памяти, проверка `divmmc` со стека | 3 (ещё +5 при divMMC) |
| выборка байта: слот, указатель страницы, смещение, `ldrb` | 4 |
| PC+1, `uxth`, запись PC в память | 3 |
| R+1 | 1 |
| загрузка и проверка `prefixOpcode` | 3 |
| сброс `flagQ` и `pendingEI` (две записи) | 2 |
| проверка границ и `tbh` | 4 |
| хвост тела: `lastFlagQ`, копия R, переход | 3-4 |
| проверка конца слайса (`stFrame`) | 3 |
| **итого** | **~29-30** |

Тела (без постоянной части):

| Опкод | Сейчас | Из них работа с памятью состояния |
|---|---|---|
| `LD A,B` | 2 (+ общий хвост) | 2 |
| `INC HL` | 8 | 4 |
| `INC B` | 21 | 7 (чтение B, запись B, флаги ×2, Q) |
| `ADD A,B` | 28 | 8 |
| `LD A,(HL)` | 16 | 4 + повторная загрузка `ts_line_t` и адреса таблицы страниц |
| `JR NZ,d` (взят) | 30 | 6 + загрузка флага NextIdle |
| `PUSH BC` | 24 | 5 |

Вывод: у типичной короткой инструкции постоянная часть больше тела, а в теле треть —
load/store состояния. Это то же, что записано в `next.md`: «~65 тактов ARM на инструкцию Z80,
дальше двигает только ядро с регистрами в регистрах».

### Что уже выжато (не повторять)

Section anchors, `exec_nocheck_ts`, `MemGates`, тик строки на следующем M1, `switch` со
вставленными телами, T/R/opCode в регистрах (opt5, −8.9% на ZEXDOC), безветочные флаги ALU,
inline ED. Отвергнуто по замеру: ядро целиком на `-O2` (−3% за +4.6 KB), inline быстрого
чтения в общие обработчики (−3.6% за +4 KB), вынос проверки `prefixOpcode` из головы (+1%:
GCC начал перезагружать адрес таблицы страниц — регистров не хватает уже сейчас).

## 2. Почему нельзя «просто объявить регистры»

- **Глобальные регистровые переменные GCC** (`register … asm("r8")`) не подходят: промежуточные
  функции других единиц трансляции вправе занять r4-r11 под свои нужды, и обратный вызов в ядро
  (`Z80::getRegPC()` из порта, ловушки, отладчик, NextIdle) увидит мусор. Геттеров/сеттеров
  снаружи ядра ~500 вызовов. Значит, состояние в памяти остаётся «истиной для внешнего мира»,
  а регистры — кэш на время слайса с публикацией перед выходом наружу. Это ровно схема `nxSync`.
- **Локальные переменные в одной большой функции** (расширение нынешнего подхода) работают,
  но распределение регистров решает GCC. В Thumb-2 callee-saved регистров 8 (r4-r11) + lr;
  сейчас 5 из них заняты адресами. На PC, A, F, BC, DE, HL, SP, T, R + база + таблица страниц
  нужно 11. Без освобождения регистров от адресов часть уедет на стек, и выигрыш съестся.
- **Рукописный/генерируемый ассемблер** даёт полный контроль, но это второе ядро рядом с C++.

## 3. Целевая архитектура

**Быстрое ядро — ускоритель счастливого пути, а не замена `Z80_JLS`.** Отношение то же, что
сейчас у `exec_nocheck_next` к `exec_nocheck`: вход при выставленных воротах, выход при любом
событии, которое быстрое ядро не обрабатывает. C++-ядро остаётся эталоном и исполняет всё
редкое: ловушки ленты/TR-DOS, точки останова, отладчик, страницы автомапа divMMC, границу
растровой строки, приём прерываний, HALT, машины с contended-памятью.

Отсюда три свойства, ради которых так и делается:

1. Покрытие опкодов наращивается постепенно: запись таблицы по умолчанию = «опубликовать
   состояние и выйти», следующая инструкция идёт через старый путь.
2. Машинно-зависимого кода в быстром ядре нет (правило CLAUDE.md про `src/speccy/machines`).
3. Любой шаг проверяется бит в бит против C++-ядра на `tools/z80bench`.

### Состояние в регистрах (вариант для ассемблера)

| ARM | Содержимое | Замечание |
|---|---|---|
| r0-r3 | рабочие | |
| r4 | база состояния Z80 (anchor) | редкое: IX/IY, WZ, I, IFF, альтернативный набор |
| r5 | T как отрицательный остаток до `min(stFrame, ts_line_t)` | граница строки и конец слайса — один `adds` + `bpl` вместо двух загрузок и двух сравнений |
| r6 | PC | |
| r7 | A | младший регистр: короткие кодировки ALU |
| r8 | F целиком, C в бите 0 | `sz5h3pnFlags` + `carryFlag` сливаются; публикация разводит обратно |
| r9 / r10 / r11 | BC / DE / HL | 16 бит, B = `ubfx #8,#8` |
| r12 | R (счётчик выборок) | r12 портят veneer'ы оверлеев — публикуется и перезагружается вокруг вызовов |
| lr | таблица страниц `MemESP::ramCurrent` | константа, после `bl` восстанавливается одной загрузкой |
| память | SP, IX, IY, WZ, Q | SP — кандидат в регистр, если замер покажет (PUSH/POP/CALL/RET) |

Ленивые вещи, которые сейчас стоят записей на каждой инструкции:

- **`prefixOpcode`** исчезает из быстрого ядра: обработчик DD/FD/ED/CB сам выбирает второй
  байт и идёт во вторую таблицу. Слайс не кончается между префиксом и опкодом. Вход в быстрое
  ядро только при `prefixOpcode == 0`; цепочки DD DD… уходят в C++.
- **`pendingEI`**: обработчик EI сам исполняет одну следующую инструкцию и выходит.
- **`flagQ/lastFlagQ`**: один регистр/слово «флаги менялись в прошлой инструкции»; пишут его
  только инструкции, меняющие F, читают только SCF/CCF. Проверить на тестах Patrik Rak (zexall
  их не ловит) — это единственное место, где возможна тихая ошибка.

### Вызовы наружу

Callee-saved регистры C-код сохраняет сам, так что r4-r11 вызов переживают. Нужна только
публикация в память и перезагрузка:

| Вызов | Публикация | Перезагрузка |
|---|---|---|
| `VIDEO::tsDrawTick` | T | T, предел слайса |
| медленный `peek/poke` (ниже 0x4000, граница строки) | T | T, предел |
| порты, `NextIdle`, batch-помощники (LDIR/INIR), ловушки | всё | всё |
| выход из ядра | всё | — |

Полная публикация + перезагрузка ≈ 20 ARM-инструкций. Вызовов — единицы тысяч на кадр
(Fluid: ~3400 `NextInt::sync`, ~460 прерываний), то есть доли процента.

## 4. Оценка ускорения

Оценка по тем же опкодам (ассемблерный вариант, не замер):

| | Сейчас | Регистровое ядро |
|---|---|---|
| постоянная часть | ~29 | ~9-10 (выборка 4, PC+1, R+1, T+предел 2, диспетчер 2) |
| `LD A,B` | 2 | 1 |
| `INC HL` | 8 | 2 |
| `INC B` | 21 | ~8 |
| `ADD A,B` | 28 | ~12 |
| `LD A,(HL)` | 16 | ~7 |
| `JR NZ,d` | 30 | ~9 |
| `PUSH BC` | 24 | ~12 |

По ступеням (ARM-инструкций на T-state, стенд z80bench в режиме Next: сейчас ZEXDOC 6.8,
«игровая смесь» 8.4):

| Ступень | Ожидание | Уверенность |
|---|---|---|
| A. C++: PC локально, префиксы внутри инструкции, ленивые Q/EI | −12…18% | высокая: это прямое удаление ~10 инструкций из ~29 постоянных |
| B. C++: A, F, BC, DE, HL локально | ещё −8…15% | низкая: зависит от распределения регистров GCC |
| C. Ассемблер, полный набор из п. 3 | −50…60% от сегодняшнего | средняя: арифметика выше, но не замер |

**Что это даёт в кадре — заметно меньше, чем в ядре:**

- Next, Fluid с музыкой: core0 18-20.8 ms, из них ядро 49-54% (~10 ms). Ступень C в пределе
  снимает 4-5 ms → 14-16 ms, кадр укладывается. Но часть этих 10 ms — вход/выход слайса и приём
  прерываний (~15 us на прерывание до fluid11), её регистры не трогают.
- Next, NXModPlayer / Atic Atac / RAMTEST: сцены упираются в рендер (core1) или в порты; выигрыш
  по FPS ноль или единицы, растёт только запас IDL.
- TS-Conf 14 MHz: ~8 из 22 ms кадра — XIP-подкачка гостевых страниц из PSRAM, ядро её не
  трогает. Ускорение ядра вдвое даёт порядка −5…6 ms на CPU-связанных сценах (fishbone, WC).
  Модель DRAM (14 MHz waits) остаётся отдельной статьёй расхода.
- Pentagon turbo, ATM/Evo, eLeMeNt, Scorpion turbo на быстром пути: тот же относительный
  выигрыш, что у TS-Conf, если они идут через `g_ts_fastmem == 2`.
- 48K/128K/+3 и всё с contended-памятью: ULA и contention вызываются на каждое обращение к
  памяти, регистры Z80 там не узкое место, и эти машины не упираются в CPU. **Не переводить.**
- GS/NeoGS и плеер работают на redcode — этот план их не касается.

|---|---|---|

| SRAM | `.nxovl` ±1 KB | цель: не больше нынешних 13.6 KB в `.nxovl` (ассемблер плотнее); для TS-пути — новый код в `.tsovl`, цена = куча TS-сессии, мерить |

| Хост-сборка | без изменений | x86-хост остаётся на C++-ядре; ассемблерное проверяется только под QEMU и на плате |
| Риск | низкий | высокий: тихие расхождения флагов/таймингов, отладка через overlay-кадры GDB |

## 6. План

### Этап 0. Измерительная база — сделан 2026-11-15

- [x] z80bench, режим Next: `Z80BENCH_MODE=next`, плагины под API QEMU 10, база на HEAD.
- [x] ARM-инструкций на инструкцию Z80 (`M1` в выводе). Гистограммы по опкодам нет: хватило
      разбивки «голова / тела» по адресам из `prof` (скрипт был разовый, в tools не попал).
- [~] Нагрузка, похожая на игру: `mkmix.py game` и `high` (код и данные выше 0x4000). Дампа
      реальной сцены Fluid/NXModPlayer с ISR нет — прерывания стенд по-прежнему не гоняет.
- [x] Сверка двух сборок: `lock` (хэш состояния по слайсам случайной длины) и `fuzz`
      (случайные инструкции, одиночные шаги и слайсы 40..103 T). Не «два ядра в одном образе»,
      а два лога, которые сравниваются `cmp`; мутационный тест ловит ошибку за 12 000 тестов.
- [x] Критерий: состояние и memcrc бит в бит на всех прогонах.
- [x] ZEXDOC и ZEXALL целиком на итоговом цикле: 67/67 OK каждый (CP/M-сборки тестов;
      сборки из `~/pico-speccy/bin` — под NedoOS, стенд их вывода не видит).

### Этап A. C++: дешёвая половина (Next) — сделан 2026-11-15, железо за владельцем

- [x] `REG_PC` → локальная `nx_pc`; `nxPub` / `nxSync` публикуют и перезагружают PC.
- [x] Проверки `prefixOpcode` в голове нет: вход только на границе инструкции, цепочка DD/FD
      выходит в общий цикл. (Вторая выборка CB/DD/FD уже была внутри обработчиков.)
- [x] `flagQ/lastFlagQ` — штамп `nx_qs`, `pendingEI` — ленивый. Проверено фаззером с SCF/CCF.
- [x] Один предел вместо двух; проверка страниц divMMC за одним сравнением `pc < 0x4000`.
- [x] Сверх плана: чтения без проверки времени (окно `NX_WIN` в голове + общий медленный

- [x] Замер, сверка, хост-стенд (NextZXOS + Fluid), тестовый ELF `debug/DVp2w-regcoreA-1.1.2.elf`.
- [ ] Железо: Fluid с музыкой, NXModPlayer, Atic Atac, загрузка NextZXOS, dot-команда esxDOS

Этот этап стоит делать в любом случае: он полезен сам по себе и уже был намечен
(«REG_PC in a register inside exec_nocheck_next»).

### Этап B. C++: A, F, BC, DE, HL локально (эксперимент на 1-2 сессии)

- [ ] Генератор переписывает `regA`, флаги, `REG_B…REG_HL` во вставленных телах; F — одно
      слово с C в бите 0.
- [ ] Смотреть objdump: сколько из них GCC реально держит в регистрах. Если на стек уходит
      больше двух — **остановиться**, результат записать в `z80-core.md`, перейти к решению по C.
- [ ] Решающее правило: B принимается только при ≥ −8% на «смеси» сверх этапа A.

### Точка решения

После A (и B) снять на железе Fluid/NXModPlayer без трассы. Если сцены, ради которых всё
затевалось, укладываются в кадр — этап C не делать, план закрыть. Этап C оправдан только если
после A/B остаются CPU-связанные сцены, где ядро > 40% core0.

### Этап C. Ассемблерное ядро (Next, затем быстрый путь TS)

- [ ] C1. Каркас: `tools/gen_z80asm.py` → `src/speccy/z80/z80fast_next.S` (не править руками),
      макросы доступа к памяти (чтение: слот+смещение; запись: ≥ 0x4000 напрямую, иначе выход),
      вход/выход с публикацией, таблица из 256 записей «выход». Стенд: lockstep проходит при
      нулевом покрытии.
- [ ] C2. Опкоды пачками по убыванию веса из гистограммы этапа 0: LD r,r' / LD r,n / LD r,(HL)
      → INC/DEC → ALU → JR/JP/DJNZ/CALL/RET → PUSH/POP → 16-битные → остальное базовое.
      После каждой пачки: lockstep + случайные потоки + замер.
- [ ] C3. CB целиком, ED (частые: LDIR через существующий batch-помощник, SBC/ADC HL, LD (nn),rr,
      NEG, RETI → выход), Z80N частые (NEXTREG → публикация + вызов + проверка ворот).
- [ ] C4. DD/FD: IX/IY из памяти; DDCB.
- [ ] C5. Размер: уложиться в окно `.nxovl`, старый `exec_nocheck_next` удалить только после
      hw-подтверждения (до этого — опция CMake `Z80_FAST_ASM`, по умолчанию OFF).
- [ ] C6. Железо: тот же набор, что в этапе A, + полный ZEXALL на плате.
- [ ] C7. Вариант для `g_ts_fastmem == 2` (16K/8K-страницы-указатели, тик `tsFastTick`, без
      модели DRAM — при `g_ts_memcyc != 0` выход в C++) в `.tsovl`. Отдельное решение после C6:
      сначала `PERF_TRACE` на TS-Conf 14 MHz, чтобы знать долю ядра против XIP.
- [ ] C8 (опционально). PC как указатель хоста с перебазированием на переходах и ремапах MMU:
      −2…3 инструкции на выборку ценой проверки пересечения слота. Только по замеру.

### Чего не делать

- Не переводить общий `exec_nocheck` и contended-машины.
- Не трогать формат состояния снаружи: `Z80::getReg*/setReg*`, снапшоты, отладчик,
  `tools/memdump.gdb` читают те же статические поля.
- Не судить по трассировочным сборкам (`NEXT_TRACE`, `PERF_HIST` раздувают голову цикла).
- JIT/динамическая перекомпиляция: самомодифицирующийся код, ремапы MMU в каждом ISR и SRAM
  под кэш блоков — на RP2350 не окупается.

## 7. Открытые вопросы

1. Сколько именно ARM-инструкций на инструкцию Z80 в реальной сцене Next (а не на ZEXDOC) —
   ответ даёт этап 0; от него зависит, стоит ли C.
2. Next на 4 MB-сборках: хватит ли flash под новый образ оверлея рядом со старым на время
   перехода.
3. Есть ли среди быстрых машин (ATM, eLeMeNt 28 MHz) сцены, упирающиеся в CPU, — нужен хотя бы
   один замер `[PERF] cpu=` на железе до C7.

Что это меняет в плане:

1. **Оценка этапа A (−12…18%) подтвердилась на ZEXDOC и превышена на игровом коде**, но
   основной выигрыш дали не «регистры», а отказ от проверки времени на каждом чтении.
2. **Этап B в прежнем виде не имеет смысла.** Закрепление переменных за регистрами
   (`register … asm("rN")`) GCC воспринимает как подсказку: значения всё равно
   перекладываются, цикл вышел на 5% медленнее. Держать A, F, BC, DE, HL в локальных
   переменных — та же лотерея распределителя; постоянная часть уже сейчас платит три
   лишних `mov` на инструкцию только за T, PC и R.
3. **Постоянная часть теперь 18 ARM-инструкций (было ~29).** Из C она не сдвигается дальше:
   три phi-`mov`, адрес таблицы страниц из literal pool на каждом обращении, проверка
   диапазона диспетчера (3), прыжок через literal pool в голове. Всё это берёт только
   генерируемый ассемблер, там же остаются load/store регистров Z80 в телах.
4. **Префиксные инструкции — отдельный резерв без ассемблера**: на `mixhi` половина времени
   уходит в `decodeDDFD` / `decodeED` / `ldx` и общие аксессоры вне цикла. Вставка частых
   DD/FD-форм (LD r,(IX+d), LD (IX+d),r, ALU (IX+d), INC/DEC IX) в цикл тем же генератором —
   дешёвый следующий шаг, если профиль реальной сцены покажет их долю (NXModPlayer: DD/FD
   малы, ED 8.4%, CB 2.6%).
5. Точка решения прежняя: снять на железе Fluid и NXModPlayer без трассы на
   `DVp2w-regcoreA`. Если ядро всё ещё > 40% core0 в сценах, не укладывающихся в кадр, —
   этап C (ассемблер), минуя B.
