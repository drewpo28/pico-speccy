## 2. Что это за машина

Настоящий Z80 на FPGA-плате Alchitry: 3.5 / 7 / 14 / 20 МГц без тактов ожидания, разгон
22 / 28 / 30 МГц. 2 МБ RAM, ещё 2 МБ с платой AA-RAM. Нет FDC: диски эмулирует esxDOS
поверх SD (DivSD). Вся расширенная периферия закрыта ZXi-портами и по умолчанию выключена:
программа сама её включает. Отсюда два вывода.

- Классическая часть почти готова: Pentagon 1024, DivSD, ULA+, Timex, TurboSound FM,
  SAA1099, Z80 DMA, Z-Controller, Gigascreen, мышь Kempston.
- Новая работа — это HGFX, URAM, FastDMA, SoundDMA, LCU, eINT, HRC/HRXC и SID.

`e_zxi_000` переключает на лету память и тайминг: 48K, 128/+2, +2A, Pentagon 128/512/1024,
Pentagon 4096, Didaktik Gama 80.

байт (`g_zxi_022/023/041/049/051/061`), а срабатывают они на запись.

## 3. Что на самом деле нужно софту

Загрузчик Nether Earth (`NETHER.COD`, код с `#4000`) разобран. Он делает так.

1. Читает `e_zxi_0FF` и требует `(v & #F0) == #E0`.
2. Читает дату ядра из `e_zxi_0FE/FD/FC` и собирает её как дату FAT:
   `год<<9 | месяц<<5 | день`. Сравнивает с `#32CB` = **2025-06-11**. Старое ядро отвергается.
3. Читает `#703B`/`#773B` и проверяет `(v & #F0) == #30` — так он отличает MB03+.

Следствия для реализации:

- Штамп ядра должен отдавать свежую дату: 2026-10-12.
- `e_zxi_0FF` = `#E1`: единственное значение в документе, проверка требует только `(v & #F0) == #E0`.
- `.APP` содержит 23 `OUT` в порты URAM: без URAM этот класс игр не пойдёт.
- Программы лежат в `.TAR` или `.TAP`, запускаются через esxDOS: отдельный формат не нужен.
- Часть софта работает только на eLeMeNt, не на MB03+ (пометка `eZX` на странице): Another
  World, HGFX-HAM videos, PF 2026, LnxView.

## 4. Как ложится на архитектуру

**Решение: отдельная архитектура `A_ELM`**, как `A_NEXT`, `A_SAM` и `A_ENT` (romset `R_ELM`).
Это самостоятельная машина со сменой личности через `e_zxi_000`, а не вариант Pentagon. Весь
код в `src/speccy/machines/Element/`. Цена: правки примерно в 60 местах (`Z80Ops::is*`, тайминг
и аудио, ROM, меню, ограничения, снапшоты), столько сейчас упоминаний `A_SAM`. Базовая личность
— Pentagon 1024. Блоки HGFX/URAM/DMA не должны зависеть от машины: так позже можно будет сделать
из них MB03+ для 48K/128K.

| Узел | Решение |
|---|---|
| Порты | В `Ports::input/output` один байтовый тест `g_elm` + вызов из flash, как у ATM/SAM. Шина: без Beta, с DivSD |
| Окна памяти | В функции записи `CPU.cpp` бит шлюза в байте `atm_ro` (занято: окна 0-3, EP 6, шрифт Evo 7; проверить бит 5). За ним маска 8K-слотов и таблица 256 B по старшему байту: VRAM, регистры, палитра, FDMA, SDMA, eINT, LCU2. Запись идёт и в RAM, и в устройство |
| Быстрые пути | `exec_nocheck`, `blockRepeat`, `MemGates`, батчи INIR/LDIR обязаны уступать слотам с окнами, иначе запись пройдёт мимо устройства |
| URAM | Слоты уже 8K (Next). 2 МБ = 128 страниц `ram[]`; страница 8K = половина `ram[n]`, запись через `plugPtr16`-подобный вызов на слот. `wantedPages` = 128 |
| HGFX буферы | PSRAM, 128 КБ, резерв в `Buffer::pageBudget` (шаблон `Ft812::configuredBytes`) |
| Горячий код | Окно на адресах `.nxovl`: Next и eLeMeNt резидентны взаимоисключающе, в сессиях других машин SRAM не тратится |
| Рендер | Целая строка на тике, как `Sam::draw`, сначала на core0. На core1 — по замерам |
| Палитра | Механизм ts256 (липкая карта, банки, reduce) уже решает 256 true color на 184-240 слотах |
| 512 px | Packed-pair (Timex hi-res, DS80) |
| Вход в меню | `p_showElm` = butter PSRAM и `FlashRoms::romsUsable()` |

### Чего не получится сделать точно

| Режим | Ограничение | Предложение |
|---|---|---|
| HGFX 2, 512x192, 256 цветов | Пара fb даёт только 16x16 цветов | 16 лучших цветов за кадр (`p80Choose` с Next), или 256 px с усреднением; выбрать на реальном софте |
| HRXC, 32 цвета | Те же 16 на кадр | Выбор цветов за кадр. HRC с цветами ZX точен |
| HGFX 3, 512x384 | В fb максимум 288 строк; повторы строк 2,1 запрещены HDMI-пинг-понгом | Сначала пропуск строк. Точный вывод на 576p, см. ниже |
| HGFX 4/5, 720x546/576, 4 цвета | Строки не помещаются в fb | Показ через строку; режим 4 уже `obsolete` |
| HGFX 7, 360x288 | Только в режимах 360 px | На 640x480 обрезка |
| 256 цветов | Пул 184 слота (240 на TMDS) | Слияние ближайших цветов, как у Kolbass |
| 20 МГц | `multiplicator` — только степени двойки | Хранить 20 в регистре, реально 14 МГц, с ограничением как `next_clk_cap`. 28 МГц в реальном времени не гарантируется |
| Прерывание по лучу, смена палитры по строкам | Частично | HRC KeyColour и INT по строке (`g_zxi_01C/1D`) работают построчно; середина строки — нет |

**HGFX 3 на 576p: память есть, узкое место — ISR.** Этап 1 — пропуск строк. Этап 2 делаем, только
если замер ISR на DVp2w покажет запас:

- Память: 384 × 256 = 98 304 B, а fb на 576p уже 103 680 B. Те же байты нарезаются на 384 ряда по
  270 B, новая куча не нужна. Чанки fb: ряд не должен пересекать границу блока.
- Драйвер читает из ряда 360 B, то есть залезет в следующий ряд. Нужен вывод «поле + 256 B + поле».
  Поднять `FB_MAX_LINES` (289). Меню и оверлеи ждут обычную разметку: возвращать её, как `blVmapSuspend`.
- Line map 384 → 576 = повторы 2,1,2,1, а `hdmi_vmap_step` требует минимум 2 строки на ряд. Нужна
  доработка ISR. Рендеров на треть больше (384 вместо 288 за кадр), срок на ряд с повтором 1 — одна
  строка, ~33 мкс при ISR 19-23 мкс. Запас мал, проверять вместе с HDMI-аудио.
- 1024x768: 512x384 ложится ровно ×2, правило «≥ 2 строки» соблюдается. Нужен режим 4 выходных
  пикселя на байт с разными цветами в паре, не проверено. Только 540/504 МГц.
- 640x480: 240 рядов, остаётся пропуск строк.
- Super HiRes из pico-amiga (пара в один пиксель) для HGFX 3 не подходит: сжатие там горизонтальное
  2:1, а здесь вертикальное 4:3 и байт packed-pair занят. Годится как запасной путь без пар
  (TFT, TV): 512 px усредняются до 256, 136 средних цветов влезают в пул 184 слота.

## 5. Фазы

Каждая фаза заканчивается проверкой на DVp2w.

### Фаза 0. Машина и детект
Арка `A_ELM`, romset, меню, ROM Pentagon + esxDOS, DivSD принудительно, Beta выключен, ZXi-регистры как файл
значений с чтением. Отдаём ID, дату ядра, COREID `eLeMeNt ZX`, MB03+ отсутствует.
Сброс и `.pss` объявлены как «не поддерживается» до конца фаз.

Проверка: esxDOS загружается, `NETHER.COD` проходит детект и не уходит на `JP NZ,#4040`.

**Сделано (2026-11-01, хост-проверка; DVp2w `debug/DVp2w-16M-elm0-1.1.1`):** `A_ELM`/`R_ELM`, Machine >
eLeMeNt ZX (butter >= 4 МБ), флаги и тайминг Pentagon 1024, 128 страниц, DivSD принудительно, Beta и
MB-02+ выключены. `Elm::portIn/portOut` (flash) держат g/e/u ZXi (768 B в куче, только на этой машине),
дату ядра 26/10/12 (двоичная: год из двух цифр), `e_zxi_0FF` = #E1, COREID, #703B-#773B = #FF, чтение
#9EFD/#9FFD, UART Uno идёт в ZiFi. Хост: esxDOS грузится, `PRINT IN` в BASIC даёт 225/26/10/12/255/101/76,
то есть те значения, которые проверяет `NETHER.COD` до `#407D`. Дальше игре нужен URAM (фаза 1).
Старт в 48 BASIC после esxDOS — то же, что на P1024 + DivSD, это не особенность `A_ELM`.
Запись `e_zxi_000`, скорости CPU и разрешения устройств пока только сохраняются.

### Фаза 1. URAM
Зоны, области, порты `#07…#73`, Protect-режим, счётчик свободных страниц, `Fast`-раскладка.
Типы памяти 0, 2, 8, 9, потом LCU/FRAM.

Проверка: CHCKURAM. `tools/elm_sim.c` (redcode + модель, как `sam_sim`/`ep_sim`) для прогонов на ПК.

**Сделано (хост):** четыре Zone по две Area, порты `#07 #27 #47 #67 #53 #73` с чтением, режимы Full и
Protect (`g_zxi_010`), `g_zxi_011/012`, запрет записи по Area, слоты держит `Elm::remap` поверх
`#7FFD`. LCU1 (типы A и C в Zone 0) сделан здесь, а не в фазе 3: `CHCKURAM` и `NETHER` считают на нём.
Protect: страницы ложатся в `ram[64..]`, 64 страницы на личности 1024 (таблица документа), старшие
зеркалятся. Типы 6, 8, 9, E пока оставляют Zone на обычной карте. `tools/elm_lcu_test.cpp` — таблица LCU.

### Фаза 2. HGFX 1: основной режим
Окна VRAM/регистры/палитра, INK/ATTR/COPY, смещения, PlanarMask, два буфера, COPY_ALL и
ERASE_ALL со статусом занятости (~6144 T и ~1 мс), прозрачность индекса 0 над экраном ZX,
ZX/линейная раскладка, индексный бордюр, рендер 256x192. Чанк через окна памяти: прямой
указатель, запись через обработчик при `PlanarMask != FF`.

Проверка: HGFXSPRI, HGFXTEXT, HGFXPLOT, HGFXBIRD, Nether Earth. Хост-тест планара против
таблицы `HGFX-2EN` (пример 145/233/143 → 153).

**Сделано (хост):** буфера 128 КБ в PSRAM, окна VRAM/регистры/палитра (таблица `Elm::wrKind` по старшему
байту: быстрый выход без вызова), INK/ATTR/COPY, смещения, PlanarMask, рабочее окно, COPY_ALL и ERASE_ALL
со статусом, chunky (типы 8, 9), индекс 0 над экраном ZX, вывод 256x192 на EndFrame поверх бордюрной
машины (`VIDEO::paper_hold`), палитра в 168 слотов. HGFXTEXT и HGFXSPRI идут. Индексный бордюр сделан 2026-11-02 (см. фазу 4).
**Nether Earth и CHCKURAM используют не HGFX 1, а HGFX 2** (`g_zxi_001 = 4`) и FastDMA: на HGFX 1 их
проверить нельзя, поэтому они остаются проверкой фаз 3-4.

### Фаза 3. FastDMA + LCU
FDMA: batch/skip, дробный skip, LDDR, fill, 24 бита, второй набор, SaveINT; копирование как один
проход с продвижением времени. CPU на это время стоит. LCU1 и LCU2. Хост-тест LCU по таблице
примеров из документа: она полная, включая деление на 0 и переполнение.

Проверка: FastDMA test, DMA Playfield Scroll, Another World.

**Сделано (хост):** FastDMA (два набора, batch/skip, плавающий skip 8.8, LDDR, fill, 24 бита, URAM),
LCU2 (результаты пишутся в RAM под окном, поэтому при бите 7 `g_zxi_060` чтение отдаёт RAM, а не регистры),
HGFX 2 с окном 64 байта на строку (12288 байт) и выводом на 256 px. Nether Earth доходит до титульного
экрана. Скорость FastDMA взята 0.5 T на байт: в документах числа нет. INT внутри передачи не откладывается
точно: время идёт кусками через `VIDEO::Draw`.

### Фаза 4. Остальная графика
HRC, HRXC, KeyLayer, Radastan, HAM, FILL, PlanarWorkingWindow, HGFX 2/3/6/7, Pentagon hi-res
(`#EFF7` бит 1), страница 6 для экрана, ULA+ `Extra`.

Проверка: HRCDEMO, KLAYTEST, RADASHOW, HGFXHAM8, HGFNICCC.

**Сделано (хост):** HRC и HRXC парами (HRXC: 32 цвета на 16), KeyLayer над ZX и HRC, Radastan, FILL, HAM8 через
куб 6x7x4 с дизерингом, HGFX 3 (через строку из 384), HGFX 4/5 (через строку, 720 только в режимах 360),
HGFX 6/7, Pentagon hi-res, первый экран в странице 6 (по кадрам). HGFX 2: по 16 цветам парами, если они
закрывают 97% пикселей, иначе 256 px. Проверено: HRCDEMO, KLAYTEST, RADASHOW, HGFXHAM8.
**HGFX 2 (режим 4) вешал плату: переполнение стека core0** (2026-11-01, perf11; HGFXBIRD и Nether Earth — оба
режим 4; на стенде шли, лог обрывался на `[ELM] extra video on (mode 4 key`, отладчик показывал core0 в
`<signal handler called>` без кадров ниже). Путь переключения в парный кадр идёт из `ESPectrum::loop` →
`EndFrame` → `Hgfx::frameEnd` → `frameSetup` (rgb/hist/hist wantPairFor2 = 2.9 КБ) → `pairPalette` (1.1 КБ) →
`samPairSync` → `profi_ds80_driver_set` → `hdmi_set_profi_ds80_mode` (2.1 КБ) — ≈7.3 КБ при стеке core0 8 КБ.
Локалы frameSetup / wantPairFor2 / pairPalette (3 КБ) теперь в блоке `Hot` (куча, только Element); остаток пути
общий с SAM/Profi/GMX, где он hw-proven. perf12 hw-confirmed DVp2w: HGFXBIRD и Nether Earth запускаются. Правило: в `frameEnd`-пути HGFX больше ни одного
массива на стеке — драйвер пар под ним берёт 2 КБ.
Все пункты фазы 4 закрыты 2026-11-02 (ниже). **PlanarWorkingWindow для chunky — не применяется по Reference:** chunky-доступ
«reflects OffsetY, PlanarMask, bit1 and bit2 of register 0» (плюс бит 4, прозрачность), окна в списке нет; `chunkyWrite` так и
делает. Вики (`hgfx:porty_registry`) описывает старую версию без `h10-h17`.
**Палитра HRXC по кадру** (2026-11-02, стенд, NOT hw-tested): Reference — «palette is always updated at the beginning of the frame,
changing it during the display process has no effect». Таблица (`#7C00` показываемого экрана, 96 B) защёлкивается в конце кадра
(`Regs::hrxc`, куча), запись в неё до `tStatesScreen` ещё попадает в этот кадр (окно `W_HRXC` на `#7C`/`#FC`, только в режиме 2),
после — ждёт следующего. Пара строится из защёлки. Тест `tools/elm_tests/hrxcpal.asm`: красный в начале кадра, зелёный после
начала картинки -> PAPER красный.
**Окна HGFX открывались и в HRC/HRXC** (найдено тем же тестом): `windowsRebuild` ставил VRAM `#40-#57`, регистры `#5B` и цвета `#5C`
при любом `mode != 0`, а в HRC/HRXC это пиксели их экрана. Байт в `#5B04` становился PlanarMask, и дальше запись пикселей съедал
движок HGFX. Теперь окна, хук чтения COPY и `hgfxOpen` только при `mode >= 3`. HRXCIMGS заметно чище (раньше блочные пятна
чужих цветов в небе и листве), KLAYTEST и TOCHIHRC покадрово те же, HRCDEMO отличается одной клеткой шума.
**ULA+ `Extra`** (2026-11-02, стенд, NOT hw-tested): группа `10` порта `#BF3B` (в Reference «proposal, not approved yet») — данные
`#FF3B` = `g_zxi_001`, чтение отдаёт его же; группы 00/01 идут в общий ULA+. Свой регистр группы (`s_ulapReg`): общий ULA+ хранит
его только при `Config::ulaplus`. Тест `tools/elm_tests/ulaextra.asm`. По пути: после выхода из HRC/HRXC (парный кадр) бордюр
оставался значением парной таблицы (коричневый) — выход из extra video теперь пересчитывает бордюр всегда.
**Индексный бордюр** (2026-11-02, стенд, NOT hw-tested): `g_zxi_020` бит 1 при HGFX 1-7 — бордюр `#FE` 0..7 = индекс таблицы
HGFX (`Hgfx::borderSlot` в `updateBorderBrd`, и поверх ULA+). Слот бордюра сверяется в конце кадра (`borderFollow`): смена цвета,
перепрограммирование, пара. В парном кадре HGFX 2 индекс бордюра добавлен в гистограмму с весом 2000 (из 4104 выборок), иначе
12 цветов пары его не брали и бордюр был чёрным. Тест `tools/elm_tests/border.asm` (5 фаз по 100 кадров). HGFXBIRD и TETRIS пишут
`g_zxi_020 = 7`: их бордюр теперь цвет индекса 0 (тёмно-фиолетовый / тёмно-серый), раньше был чёрный ZX; HE2025 (5) не меняется.
Режим COPY (wiki, регистр 01): копирует 8 пикселей из кэша, только если записан тот же байт, что перед этим
прочитан; запись без чтения рисует как ATTR (ink h03, paper h0E). Хука на чтение нет: "было чтение" значит, что
байт равен памяти под окном, поэтому запись в окно VRAM в RAM не проходит.
**Источник COPY — позиция ЧТЕНИЯ (+ S_OffX/Y), а не записи** (2026-11-01, стенд — HE2025 меню и игра совпадают
с эталоном; hw-confirmed DVp2w 2026-11-02). Вики: «значения, которые Z80 читает и пишет, не важны», и ROM-скролл (LDIR строка y+8 → y)
работает в этом режиме — значит пиксели берутся с адреса чтения. HE2025 рисует фиолетовую сетку так: 2 байта ATTR,
затем LDIR HL→HL+2 по строке (самоперекрывающееся размножение); у нас источник брался с адреса записи, и сетка
оставалась обрывками (те «артефакты», elm-all тоже). Спрайты она блитит `LD A,(HL) / LD (DE),A / INC D` — чтение по
одному адресу окна, запись по другому, строкой ниже; на этом сыпались «лишние точки» в игре/демо. Поэтому **настоящий
хук чтения**: `Elm::g_elm_vram_rd` (ненулевой, пока окно VRAM замаплено и режим COPY) — один тест в `gsDmaPeek8`
(CPU.cpp, общая воронка чтений, как g_timex_mmu / g_ngs_zxdma), `Elm::memRead` запоминает смещение чтения в окне и
взводит защёлку; запись в окно в режиме COPY берёт её (один раз) или рисует как ATTR. Запись мимо окна защёлку НЕ
сбрасывает (hw-confirmed DVp2w 2026-11-02): сброс на стековой записи (CALL/PUSH между чтением и записью) давал на плате
«точки» в HE2025, а на стенде сброс был выключен по умолчанию — код стенда и платы расходился. Эвристики «байт == RAM под окном»
и сниффера LDI больше нет. **Z80 DMA и FastDMA читают через `Elm::busRead`** — их чтения тоже взводят защёлку (вики:
скролл делается и fDMA, и обычным DMA); без этого HGFXAGON (копирует экран DMA) превращался в кашу. Окно на #4000 и выше
требует отключить быстрый путь чтений (`Elm::fastReadOk()` в правиле `tsFastMemRecalc`); HE2025 держит окно на #2300 —
бесплатно. `Q_RUN` двухсловный (второе слово = смещение чтения), прогон рубится по строке и источника, и назначения;
перекрывающаяся копия вперёд словами = побайтовой (шаг ≥ 8 байт). Стенд: HGFXAGON покадрово идентичен прежней сборке,
HGFXBIRD без изменений, HE2025 меню/игра/демо чистые. Z80 DMA на машине включён всегда и
пишет через окна (HGFXBIRD, HGFXAGON).
PlanarMask 0 ничего не рисует, и запись проходит в RAM: HE2025 так кладёт стартовый код в #4000 под открытым окном.
e_zxi_02D бит 7 = 0: при URAM в Zone 0 точки входа divSD не срабатывают (`g_elm_nodiv`), иначе `JP #0000` в
Paradise уходил в esxDOS и HGFX не открывался, герой пропадал.
**Два ядра (как TS-Conf и Next):** core0 кладёт записи VRAM, регистры и команды в очередь (16K записей, PSRAM), core1 ведёт
движок (`s_e`, свои регистры) и рисует кадр; кадр, на который core1 не успел, не рисуется, а записи его выполняются. HGFX
только читает `s_r` на core0. При чанки-окнах (`direct`) движок остаётся на core0. 8 пикселей пишутся двумя словами
(`put8`), если всё на экране и нет окна. Причина: HGFXAGON 7800 записей COPY за кадр, 62k попиксельных чтений/записей PSRAM.
Пока HGFX владеет картинкой, Draw = Blank и работает быстрый путь памяти уровня 1 (как VDAC2 на TS-Conf). Сброс снимает
`g_elm_nodiv` (иначе F11 после игры с URAM в Zone 0 шёл мимо esxDOS в меню 128) и чистит буферы HGFX.
Подряд идущие записи COPY склеиваются на core0 в одну запись очереди (`Q_RUN`, байт не важен): PERF-лог HGFXAGON показал
27 мс движка на 8460 записей и очередь, забитую до конца.
**ОДИН буфер HGFX 1 в SRAM (48 КБ, шесть блоков по 32 строки — куча лежит регионами), и только когда он нужен** (2026-11-01,
hw-confirmed DVp2w: HGFXAGON 48.7 FPS, `sram=10`): `sramPromote` после 15 отстающих кадров из 30 переносит буфер, которому PSRAM
обошлась бы дороже (`s_use`: запись = fill + write-back, т.е. ×2, чтение ×1, отрисовка и команды 1/2 учтены), второй не переносится
никогда (`SRAM_MAX`); отказ кучи повторяется через 10 с, не на сеанс. Память возвращается в кучу при выходе программы из HGFX
(`extra video off`), смене режима, окне chunky и F11 (`[ELM] HGFX buffer N back to the heap`). Арифметика, почему без SRAM 50 FPS
нет: строка XIP 8 байт, COPY = fill src + fill dst + write-back, плюс чтения отрисовки — у HGFXAGON ~20k промахов на кадр
(1.17M/с против 0.19M/с), ~18 мс core1; оба буфера в SRAM давали 9 мс движка, один — 12.8 + draw 6. Прогоны COPY идут построчно
и в ZX-раскладке (группа 32 байт = одна строка): побайтовый путь стоил 9 мс даже в SRAM. Горячий код движка в окне `.dmaovl`
(на Elm загружено всегда, поэтому вход в Elm всегда с перезагрузкой). Кадр рисуется, когда луч вне картинки, иначе спрайты рвутся. core0 ждёт core1 в конце
кадра: пропуск кадров давал отставание на 10 кадров и 5 кадров из 60 на экране.
Окно PlanarWorkingWindow вне экрана ничего не ограничивает: догадка, иначе HGFXSPRI мигает через кадр.
**HGFNICCC** (3D исправлено 2026-11-02, стенд, NOT hw-tested): 3D-часть (поток кадров STNICCC, FILL) не рисовалась вовсе —
плеер ждал на `HALT` кадр `#820D`. Демо пишет `e_zxi_000 = 05` (Pentagon 128) и кладёт поток в 120 страниц Protect URAM; у нас
Protect был всегда 64 страницы (личность 1024), старшие зеркалились и затирали начало потока. По таблице Reference Protect = 128
страниц при ZX RAM до 512 КБ, 64 при 1024: `protectPages()` следует `e_zxi_000` (7/8 -> 64, иначе 128), база та же `ram[64..]`,
верхние 64 страницы — `ram[96..127]` (на машине там divRAM, у нас он отдельно). Смена личности в остальном (тайминг, память ZX)
по-прежнему не моделируется. Записи `+24..28` страницы регистров — ложный след: регистры на `#BA00`, там же код обработчика
прерываний и его переменные. Открыто: `h0F FillPlanarMask` (в Reference только название) — FILL его не учитывает; проба «заливка
только по планам маски» на HGFNICCC ничего не изменила (число тонких чёрных полос то же), поэтому не принята.
HGFX 3-7 и текст HGFX 2 тестовой программой не проверялись.
**Запись в окно VRAM доходит и до RAM** (2026-11-02, стенд, NOT hw-tested): раньше `memWrite` её поглощал (наследие эвристики COPY
«байт == RAM под окном», её заменил настоящий хук чтения). HGFXCUBE стирает буфер так: `#FF` в `#E000` с индексом 0, затем Z80 DMA
`#E000 -> #E001` на `#17FF` байт; поглощённый `#FF` давал размножение старого 0, INK с байтом 0 ничего не стирал, вокруг куба копились
прошлые кадры. HGFX-6EN подтверждает: прокрутка ROM в режиме COPY читает из окна те байты, что сама туда записала. Теперь куб чистый
и двигается, HGFXTEXT показывает блок «COLOR» и «scroll?»; HE2025 покадрово тот же, TETRIS/HGFXBIRD — то же (кроме фазы бегущей строки).
HGFXTEXT/PLOT/ELOG/CUBE/SPRI — все HGFX 1.
**Окно VRAM всегда 6144 байта** (2026-11-02, стенд, NOT hw-tested): HGFX-4EN — «VideoRAM space of 6144 bytes is enough for half of
the HiRes screen only ... we help ourselves with an offset». Окно росло с режимом (48 страниц в HGFX 2, 96 в HGFX 3 = `#4000-#9FFF`)
и в SHRTEXT (HGFX-SHR, режим 5) накрывало стек, код и текстовый буфер программы: их записи рисовались точками. Теперь 24 страницы;
Nether Earth (титул, бегущая строка), HGFXBIRD и рабочий стол SHR покадрово те же.
**Проверено на стенде по режимам (2026-11-02):** HGFX 3 — HGFX-SHR оба примера (рабочий стол 2x2 ZX-экрана, текст мелким шрифтом;
по вертикали каждая вторая строка из 384, как в плане); HGFX 1 chunky + HAM — HGFXDEM2 (zoom лисы, HAM-градиент). Ввод команд esxDOS
на стенде — генератор нажатий (scratchpad `keys.py`: `.cd E/X`, `LOAD *"X.BAS"`), папки в `~/pico-speccy/E/`. HGFX 4-7: в подборке
владельца программ пока не нашлось (PF2026/AWORLD/RADSCROL — в очереди отдельно).
**TETRIS (Zirin 2026) без фона-фото и «негатив» на титуле Nether Earth** (2026-11-02, hw-confirmed DVp2w тем же днём, владелец: «работает», не детализировано;
`debug/DVp2w-elm-tetris-1.1.1`). Три причины. (1) FastDMA: Тетрис пишет `h10 = 3` (24 бита, источник URAM) один раз,
а каждую полосу фото запускает записью `h00`; запись `h00` при бите 0 в `h10` теперь идёт 24-битной передачей (Reference
говорит только «запись h10 запускает»). (2) Раскладка памяти 9 (`RAM Area0 & HGFX Area1`): окно HGFX в Area1 начинается
с OffsetY, а не с OffsetY + 32 строки: Тетрис пишет каждую 32-строчную полосу в `#2000` при `OffsetY = строка`. Для
раскладки 8 Area1 по-прежнему +#2000. (3) `paletteProgram` раздавал 168 слотов заново в порядке появления цветов: при
затухании палитры номера слотов плыли каждый шаг, а core1 перерисовывает кадр позже, и старые пиксели на кадр
показывались под новыми номерами (механизм Kolbass на TS-Conf). Теперь раскладка липкая: индекс держит слот, смена
цвета пишется в тот же слот; новый слот берёт только индекс, разошедшийся с соседями по слоту.
(4) Бегущая строка на титуле Nether Earth («SAA MUSIC: MBORIK 2025») была сплошной розовой полосой: скроллер —
COPY `LDIR #C000→#C000` с вторичным OffsetX = 3 и маской C0, новая колонка букв рисуется справа INK-ом. Источник COPY
за правым краем строки мы пропускали, и биты 6-7, поставленные INK-ом у края, не гасли и размазывались скроллом.
Теперь пиксель источника вне строки читается как 0. HE2025 и HGFXAGON покадрово те же.

## 6. Риски

- **Нет RTL.** Поведение планарного чтения, момент применения палитры HGFX, точные такты
  `COPY_ALL`, тайминг FDMA под SoundDMA документированы слабо. Нужен LnxSpectrum (Windows;
  здесь `wine` не найден) или ответы автора.
- **Цена записи.** Запись в планар с `PlanarMask` — до 8 байт в PSRAM на один байт Z80. При
  кратных 8 смещениях это одна строка XIP-кэша, иначе две. На 14 МГц со спрайтами — главный
  неизвестный по FPS. Смотреть на HGFXSPRI в PERF-сборке.
- **Flash.** Образ DVp2 на 4 МБ уже занимает около 3.5 МБ. Правило проекта: что не влезло в
  4 МБ, идёт за флаг как `MOONSOUND`. Нужно измерить после фазы 2.
- **Куча 576p.** Окно кода + буферы строк отнимают кучу так же, как на Next. Окно делить с `.nxovl`.
- **Быстрые пути** Z80 — самый вероятный источник тихих ошибок: запись мимо устройства не падает,
  а просто не рисует. Нужен отладочный счётчик записей в окна.
- **Быстрая эволюция.** Ядро меняется (октябрь 2026: новые режимы и eINT). Ориентир — ревизия
  20261012, Reference скачать и сохранить в `debug/`.
